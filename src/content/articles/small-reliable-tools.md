> 示例文章 · 仅用于演示，不代表作者真实经历。

一个脚本可能最初只为解决一次问题而写。真正的变化发生在第二次使用：调用者开始依赖它的行为，也开始把它的结果交给下一步流程。此时，工具是否可靠就不只是实现细节，而是能否帮助我们减少不确定性。

## 把输入写在边界上

优先让调用者显式提供目录、文件名和模式，避免工具悄悄遍历不相关的位置。输入校验应当在工作开始之前完成；如果缺少必要参数，直接说明缺少什么，比执行到一半才失败更容易理解。

```typescript
export function parsePositiveInteger(raw: string): number {
  if (!/^\d+$/.test(raw)) {
    throw new Error("请输入正整数");
  }
  const value = Number(raw);
  if (!Number.isSafeInteger(value) || value < 1) {
    throw new Error("数值必须是安全范围内的正整数");
  }
  return value;
}
```

这段示例故意只支持一种输入形式。范围越清楚，错误提示和测试就越容易保持一致。

## 让失败能够被看见

失败信息需要说明正在做什么，以及下一步可以检查什么。不要把所有异常都转换成一个含糊的「操作失败」，也不要在面向用户的提示中输出可能包含私密信息的完整环境。

对于批量处理，区分已成功、未处理和失败的项目。这样即使中途停止，也能够判断哪些动作可以安全重试。

## 为重复执行设计

同一条命令运行两次，会覆盖什么、追加什么、还是得到相同结果？把这件事明确写进说明，比增加许多可选参数更重要。涉及文件写入时，可以先提供预览结果，让调用者理解变化范围。

> 可靠的小工具，不一定处理所有情况，但应该让它支持的情况足够明确。

为最常见的成功路径、一个边界输入和一个失败路径留下测试，通常就能显著提高后续修改的把握。工具可以小，约定应当清楚。
