> 示例文章 · 仅用于演示，不代表作者真实经历。下面的程序是为讲解阅读方法编写的简化示例。

面对陌生的代码库，从第一个文件开始逐行阅读，通常不是最容易建立理解的方式。目录结构告诉我们代码被放在哪里，却未必告诉我们一项行为是怎样发生的。选择一个足够具体的用户行为，沿着它走完一次输入到输出的过程，往往更有效。

这里的「最短路径」并不意味着忽略复杂性，而是先找到一条能够贯穿系统的线。沿途遇到尚不理解的分支，可以记下问题，等主线清楚之后再回来。

## 选择一个能够复现的行为

「理解整个解析器」太宽泛，「输入一行带注释的配置后，会得到什么结果」则足够具体。后者能够对应一个测试、一段输入和一个明确输出，也更容易判断阅读是否真的产生了理解。

开始之前，可以写一张三行的阅读卡：输入是什么、从哪里进入、最后应该看到什么。此时即使对内部结构一无所知，也已经有了可验证的目标。阅读过程中如果发现预期有误，就修改卡片，而不是悄悄改变问题。

## 沿着数据流追踪

下面是一个刻意保持简单的配置读取函数。第一遍阅读时，先不讨论它应不应该支持更多语法，只观察输入经过了哪些变化。

```typescript
type ConfigLine = { key: string; value: string };

export function parseLine(input: string): ConfigLine | null {
  const content = input.split("#", 1)[0].trim();
  if (!content) return null;

  const separator = content.indexOf("=");
  if (separator < 1) throw new Error("配置行缺少有效键值对");

  return {
    key: content.slice(0, separator).trim(),
    value: content.slice(separator + 1).trim(),
  };
}
```

这条路径包含四个动作：移除注释、清理首尾空白、寻找分隔符、构造结果。把它们写下来，就有了第一层模型。随后再问：如果值里也有井号会怎样？空值是否允许？键只包含空格时是否应该报错？这些问题来自实际代码，而不是阅读之前的猜测。

局部实现不等于最终契约。调用方可能在进入这个函数之前做过校验，也可能在返回之后补上默认值。阅读到边界时，应当查看调用点，确认约束究竟由哪一层负责。

## 区分控制流和状态变化

控制流解释「下一步会走到哪里」，状态变化解释「什么东西在这一刻变得不同」。两者并不总是同一条线。一个函数可能只有几行，却改变了共享对象；另一个函数可能很长，但只是根据输入生成一个新结果。

在笔记里，可以用一张简单表格把两者分开：

| 位置 | 输入 | 输出或状态变化 | 需要确认的问题 |
| --- | --- | --- | --- |
| 入口 | 原始文本 | 单行字符串 | 编码怎样处理 |
| 解析 | 一行字符串 | 键值对象或空值 | 错误在哪里呈现 |
| 合并 | 多个键值对象 | 配置对象 | 重复键采用什么规则 |
| 使用 | 配置对象 | 具体行为 | 缺失值是否有默认值 |

表格不需要覆盖整个代码库。它的作用是把当前路径中的假设暴露出来，避免我们因为函数名看起来熟悉，就跳过关键的状态语义。

## 用测试检查自己的解释

读完一段代码之后，尝试先预测一个新输入的结果，再运行测试。预测与实际不一致的地方，往往就是模型中缺失的部分。此时不必急着改代码，先解释差异从哪里产生。

对于前面的示例，可以尝试空行、纯注释、缺少等号和包含多个等号的输入。每一个用例只回答一个问题。等到这些局部行为清楚之后，再考虑这个解析规则是否符合产品需求。

> 阅读源码的进展，不是看过多少行，而是能够用多少个具体例子解释它为什么这样工作。

## 回到结构，补上地图

走完一条路径后，再观察目录结构和模块边界，会比刚开始时更容易理解。此时模块名称不再只是抽象标签，而是与已经观察到的数据和行为对应起来。

最后留下一份简短的路径记录：入口函数、关键转换、错误出口，以及还没有探索的分支。下次回来时，这份记录能帮助我们迅速恢复上下文。如果系统后来变化，也可以沿着同一条行为路径重新验证。

从一个小问题出发，获得一条清楚的路径，再慢慢扩展相邻的分支。陌生代码不必一次全部掌握，但每一次阅读都可以留下一个可靠的支点。
