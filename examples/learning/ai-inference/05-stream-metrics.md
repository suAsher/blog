## 一条流式事件不一定只有一个 token

构造一次请求：零秒发出，半秒收到第一批输出，零点八秒收到第二批，一点二秒结束。每批恰好携带两个 token。下面只做确定性的时间线算术，不发请求、不使用墙钟，也不声称是网络或模型实测。

```python
sent_at = 0.0
events = [(0.5, 2), (0.8, 2), (1.2, 2)]
ttft = events[0][0] - sent_at
event_gaps = [events[i][0] - events[i - 1][0] for i in range(1, len(events))]
output_tokens = sum(count for _, count in events)
mean_after_first = (events[-1][0] - events[0][0]) / (output_tokens - 1)
assert round(ttft, 2) == 0.5
assert [round(gap, 2) for gap in event_gaps] == [0.3, 0.4]
assert round(mean_after_first, 2) == 0.14
print("TTFT", round(ttft, 2))
print("event gaps", [round(gap, 2) for gap in event_gaps])
print("arithmetic token average", round(mean_after_first, 2))

```

输出首响为零点五，两个事件间隔为零点三和零点四，最后一个平均值为零点一四。这里的事件特指携带生成内容的输出，不包括空的元数据事件。它们使用不同分母，不能互相替代。尤其不能把两个输出事件之间的间隔，当成已精确观测每个内部 token 的生成时间。

## 对照实际引擎的指标口径

[vLLM 指标设计文档](https://docs.vllm.ai/en/latest/design/metrics/)区分按流式输出事件记录的间隔与按已完成请求记录的每输出 token 平均耗时。具体名称和实现可能随版本演进；排障记录应写下引擎版本、指标定义和采集位置。客户端首响还可能包含传输与入口处理，不能直接与服务端某个阶段相减后就认定差值全是网络。

对于只输出一个 token 的请求，“扣除首响后再除以输出数减一”没有合法分母，应单独处理。失败、超时、取消和正常结束也需要分开统计；把失败请求直接从报告中删掉，会让延迟看起来更好，却掩盖服务的实际可用性。

## 做一个最小测量表

先保存请求数、成功数、失败原因、输入与输出长度，再保存采样时间线。报表同时呈现样本数量、单位和分位数算法，而不是只给一个漂亮均值。输入分布改变后，应作为新实验记录，不能与旧报告无条件合并。

练习将第二个事件的 token 数改为一个，观察事件间隔保持不变而算术平均值改变。再加入一个零输出请求，写出你希望报告如何呈现它。最后解释什么情况下代理缓冲会使客户端事件比模型内部步骤更粗。

这些构造数据没有证明某个引擎快或慢。它们用于训练你先问“这个数记录的到底是什么”，再解释曲线变化。
