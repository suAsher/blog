## 先写下三种地址

一个服务需要区分容器内进程的监听地址、容器网络中的地址、宿主机发布的地址。客户端究竟从哪里发起请求，决定它应该访问哪一层。仅仅在镜像里声明端口，不会自动让服务出现在公网，也不能证明进程已经监听。

下面是结构示意，不是可直接执行的完整命令。`LOCAL_IMAGE` 必须替换成经过检查的本地镜像，镜像里的程序也必须实际监听容器内的八千端口。

```bash
docker run --rm \
  -p 127.0.0.1:18080:8000 \
  --mount type=volume,src=learning-content,dst=/data \
  LOCAL_IMAGE
```

这里把宿主机回环地址的一万八千零八十端口映射到容器端口，数据卷则挂到 `/data`。它们分别解决可达性和数据存放位置，不能互相代替。实际访问边界还取决于Docker版本、网络环境与其他代理；不要把这段配置当作独立的完整安全方案。

## 数据寿命不跟程序实例绑定

镜像适合保存应用程序，持续变化的内容应明确放在持久存储中。重新创建容器后，临时写入容器可写层的文件可能无法按预期保留；数据卷的备份则需要另外计划。备份源码或镜像，不等于备份博客文章、上传图片或数据库状态。

如果服务由多个进程写入，备份时还要考虑一致性。文件存在并不意味着它们来自同一时刻。单写入进程的小系统可以用维护窗口简化一致备份，但恢复流程仍应实际演练，并保留正确权限。

## 验证顺序

先在容器内检查进程监听，再从宿主机回环地址访问，最后才检查反向代理和认证。给每一层分别写出预期失败形态：未监听、映射错误、代理拒绝、账号未登录。存储练习则创建一份纯演示内容，重建实例后核对是否仍在，不读取真实用户数据。
