## 三次重试并不一定能装进五秒

假设一次请求最多花两秒，第一次失败后等待一秒，第二次失败后再等两秒。仅这些上限就可能超出调用方允许的总时长。把“每次超时”和“最多重试次数”分别写到配置文件，并不能自动得到一个合理的总预算。先明确调用者愿意等多久，再决定剩余时间是否值得发出下一次尝试。

```python
budget = 5.0
spent = 0.0
outcomes = [(1.0, False), (1.0, True)]
backoffs = [0.5]

for attempt, (duration, success) in enumerate(outcomes, start=1):
    if duration > budget - spent:
        print("budget exhausted")
        break
    spent += duration
    print(attempt, success)
    if success:
        break
    delay = backoffs[attempt - 1]
    if delay >= budget - spent:
        print("no budget for retry")
        break
    spent += delay
print(f"spent={spent:.1f}")
```

输出为 `1 False`、`2 True`、`spent=2.5`。这是构造的确定性时间轴，不是网络实测，不会等待或发送请求。将第二次耗时改成四秒，再观察预算如何阻止下一次尝试。记录这个变化，练习从总时间而不是从配置项数量理解行为。

## 为什么有些操作不能直接重发

超时意味着调用方没有在约定时间内拿到结果，不一定意味着对方没有执行。读取一次状态与创建一次付费任务，失败后的处理方式应不同。需要重试的写操作应有明确的幂等标识、去重范围和收据保留机制；单靠客户端“我只点了一次”不能提供服务端保证。幂等键本身也不能取代身份验证或并发版本检查。

## 从模拟走向真实程序

实际程序应用单调时钟计算经过时间，用剩余预算约束连接、读取与退避；还要保留取消信号。随机抖动能减少同时重试的集中冲击，但不能解决无上限的并发或无限队列。错误是否短暂、重试是否安全、有没有剩余预算，是三个独立问题。

本节练习把预算设为零、把第一次结果改为成功，再为两种情况分别写断言。不要把这个短循环当作通用重试库：它没有取消传播、动态耗时和传输错误分类，作用是让时间成本先变得可见。
