## 先有记录，再给原因起名字

下面的输入是手写的演示观测，不来自真实服务器。先用程序判断它支持哪些结论，再写排查笔记。两个请求的总时长不同，并不能直接推导成 CPU、网络或模型的问题；我们需要明确每个字段的测量位置，以及同一次请求中这些数字如何关联。

```python
observations = [
    {"id": "demo-a", "status": 200, "queue_ms": 20, "work_ms": 80},
    {"id": "demo-b", "status": 200, "queue_ms": 140, "work_ms": 80},
]

for item in observations:
    known_ms = item["queue_ms"] + item["work_ms"]
    print(item["id"], known_ms, item["queue_ms"] > item["work_ms"])
assert observations[0]["work_ms"] == observations[1]["work_ms"]
```

输出为 `demo-a 100 False` 与 `demo-b 220 True`。能确认的是这组输入中的处理字段相同，而排队字段不同；不能确认的是整个真实端到端延迟等于字段之和。客户端等待、代理缓冲和测量遗漏都可能存在。笔记中应写“已知阶段合计”，不要把未测量的部分默认为零。

## 在 Linux 上怎样逐层补证据

检查自己的练习服务时，先记录时间窗口和 PID，再观察该进程的状态、监听地址和应用日志。`ps -p <练习PID>` 关注身份与状态，`ss -ltn` 查看本机监听情况；它们不会替你证明某个 HTTP 路由成功。不要对未知公网地址扫描端口，也不要用重启或删除日志来“试一下”。工具输出可能包含路径与连接信息，分享前需要筛掉真实用户数据。

## 让每个假设只有一个验证动作

若猜测是排队，下一步记录队列长度和入队时间；若猜测是请求大小变化，下一步固定输入；若猜测是名称解析，下一步分别记录解析与连接时间。一次改动多项参数，即使现象消失，也难以知道哪项解释成立。用相同输入重做实验，并保留成功与失败的样本，才能避免只挑符合猜测的数据。
