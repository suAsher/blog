## 一次故障，不应放大成无休止的请求

服务暂时不可用时，立即循环重试看起来容易恢复，却可能让已经拥塞的服务收到更多负载。重试也会消耗调用者的等待预算。若上层等待两秒，下层每次都等待两秒再重试三次，用户实际付出的时间就不再是界面承诺的两秒。预算必须跨尝试传递，而不是每次重新开始计时。

下面只生成一份退避计划，不真正 sleep，也不向任何服务发请求。每次尝试成本设为固定示例值；下一次等待连同尝试成本超过剩余预算时就停止。数字都是构造输入，不能当作线上延迟分布。真实程序应使用单调时钟测量经过时间，并把连接、排队和执行成本纳入预算。

```python
def retry_plan(total_ms, attempt_ms, waits_ms):
    elapsed = 0
    attempts = 0
    for wait in [0] + list(waits_ms):
        if elapsed + wait + attempt_ms > total_ms:
            break
        elapsed += wait + attempt_ms
        attempts += 1
    return attempts, elapsed

assert retry_plan(1000, 100, [100, 200, 400]) == (3, 600)
assert retry_plan(50, 100, [100]) == (0, 0)
print(retry_plan(1000, 100, [100, 200, 400]))
```

输出 `(3, 600)`，第四次尝试会使总成本超过预算。练习改变预算和单次成本，列出停止原因；再给多个客户端加入不同的退避抖动，比较等待是否集中在相同时刻。抖动帮助分散重试时机，但不会凭空增加系统容量。

## 演练需要可解释的终点

真实恢复策略还要区分永久错误、可重试错误和未知提交结果。重试具有副作用的操作前，需要上一章的幂等与收据约定；预算用完后应向调用者返回明确状态，保留排查线索，不继续在后台偷偷重试。本例不模拟超时取消、并发争抢或服务恢复，不保证重试一定成功。把尝试次数、停止原因、剩余预算和请求标识记录下来，才能判断恢复是在帮助系统，还是在扩大故障。
