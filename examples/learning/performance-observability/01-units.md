## 三十个请求，不能只报一个数字

一组串行练习完成三十个请求，每个请求用时二十毫秒。总耗时是六百毫秒，对应每秒五十个请求。二十毫秒是单次延迟，五十每秒是吞吐率，两者描述的对象不同。换成并发执行以后，不能再直接用延迟的倒数声称吞吐；还需要说明并发数量、共享资源和实际测量窗口。

下面统一把输入转换成秒，输出时再明确单位。程序使用人为构造的数据，不发起真实请求，也没有测量任何机器性能。用断言先验证计算口径，可以减少图表里把毫秒当秒、把请求数当速率的错误。报表中应把单位写进字段名，避免接收方猜测一个裸数字代表什么。

```python
durations_ms = [20] * 30
elapsed_seconds = sum(durations_ms) / 1000
throughput_rps = len(durations_ms) / elapsed_seconds
mean_latency_ms = sum(durations_ms) / len(durations_ms)
assert elapsed_seconds == 0.6
assert throughput_rps == 50
assert mean_latency_ms == 20
print(f'{throughput_rps:.1f} requests/s, {mean_latency_ms:.1f} ms/request')
```

预期输出 `50.0 requests/s, 20.0 ms/request`。练习加入三十个失败请求，分别定义尝试吞吐和成功吞吐，再回答失败延迟是否进入统计。没有唯一适合所有场景的口径，但相同曲线不能在不同时间悄悄改变分母。

## 给测量窗口一个边界

如果统计十秒窗口内完成的请求，跨窗口开始、结束的请求如何归属，需要提前约定。短窗口受突发和计时误差影响，长窗口又可能掩盖短时拥塞。人工例子里的串行成本之和不包含启动、排队或清理开销，因此它不等同于真实墙钟时间。正式实验应同时保存输入规模、并发、成功率、窗口和环境；先把范围对齐，后续的分位数和排队讨论才不会比较两种不同的工作负载。
