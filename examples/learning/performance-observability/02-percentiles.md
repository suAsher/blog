## 大多数很快，少数却等很久

构造一百个请求，其中九十五个耗时十毫秒，另外五个耗时一千毫秒。平均值会升高，却不能告诉你有多少人经历了长等待。分位数提供另一种观察方式：在指定排序和插值约定下，用一个位置描述样本的边界。比较不同工具的分位数时，先确认算法和样本范围，不能只比较字段名。

下面明确使用 nearest-rank 约定：先排序，取向上取整后的排名，排名从一开始。它适合说明概念，不是所有统计库的默认算法。这个样本的百分之九十五位置仍是十毫秒，百分之九十九位置则落在慢请求中。数据完全构造，结果只是算术验证。

```python
from math import ceil

def nearest_rank(values, percentile):
    if not values or not 0 < percentile <= 100:
        raise ValueError('invalid sample or percentile')
    ordered = sorted(values)
    return ordered[ceil(percentile / 100 * len(ordered)) - 1]

latencies = [10] * 95 + [1000] * 5
assert nearest_rank(latencies, 95) == 10
assert nearest_rank(latencies, 99) == 1000
assert sum(latencies) / len(latencies) == 59.5
print('p95=10 ms, p99=1000 ms, mean=59.5 ms')
```

练习把慢请求数量改成六个，再重新计算 p95。少量样本中，新增一条记录就可能让高分位数明显跳动。特别是样本很少时，报告 p99 并不会自动带来精确性；应一并展示请求数量、错误数和分布轮廓。

## 不要平均两组 p99

两个实例的 p99 不能简单取平均后当成整体 p99，因为各实例的样本量和分布不同。要么保留可合并的分布信息，要么汇总足够细的桶并说明近似误差。还要检查超时和失败是否被排除：丢掉最慢的请求，曲线可能看起来更漂亮，用户却体验更差。本例不实现流式直方图，也不证明任何服务等级目标，只训练读者把统计定义与用户等待联系起来。
