## 两次平均值，并不是一份完整实验

你改了一段程序，第二次运行的平均耗时更低，这值得继续调查，却还不能说明修改必然有效。输入规模、缓存、后台负载和执行顺序都可能影响结果。先写下假设：这次修改预计减少哪一阶段的成本，哪些指标可能变差，再决定如何收集数据。否则很容易只保留支持预期的那一条曲线。

下面用同一组构造工作项的前后成本计算成对差值。正差表示本例里 after 更小，零差表示没有变化；程序还保留一个退步样本，不把它删掉。这里没有执行真实基准，也没有得出统计显著性的结论，它只验证比较方法和输出方向。

```python
before_ms = [100, 120, 80, 90, 110]
after_ms = [90, 100, 85, 90, 95]
assert len(before_ms) == len(after_ms)
differences = [before - after for before, after in zip(before_ms, after_ms)]
assert differences == [10, 20, -5, 0, 15]
assert sum(differences) / len(differences) == 8
regressions = sum(value < 0 for value in differences)
assert regressions == 1
print('mean difference=8 ms; regressions=1')
```

练习改变输入排序，并写出真实实验如何交替运行不同版本，以减少某一种运行顺序独占热缓存的影响。还应同时检查错误率、资源使用和尾部延迟。平均少八毫秒但错误增加，可能不值得发布；一个只对小输入有效的优化，也不应宣传成普遍提速。

## 记录足够重做，而不是堆满机器信息

保存必要的代码版本、输入生成方式、并发度、预热约定、重复次数和原始结果。配置中可能包含路径或私密业务数据，公开笔记只保留脱敏且必要的信息。本例没有置信区间、随机化或多环境重复，因此不能用于外推生产收益。真正有用的结论应写明观察范围、反例以及下次怎样推翻它；保留这些边界，会让未来的自己少重复一次错误实验。
