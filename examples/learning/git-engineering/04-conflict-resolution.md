## 构造一个没有业务风险的冲突

在独立练习仓库先提交 `mode=base` 到 `settings.txt`。记录当前分支名，再创建 `experiment` 分支，把该行改成 `mode=experiment` 并提交。回到原分支，将同一行改成 `mode=main` 后提交。现在执行合并：

```bash
git merge experiment
```

命令应报告冲突，返回非零状态。冲突不是仓库已经损坏，而是两条历史对相同位置提供了不同答案，工具没有足够业务语义替你选择。打开文件会看见冲突标记，标记两侧的内容都应先读懂。

## 不把“保留哪边”当作全部工作

如果原分支改变的是默认部署模式，而实验分支改变的是新模式名字，最终结果也许需要第三个值。解决冲突要回答的是合并后的行为应该是什么。简单删除标记并不证明逻辑正确，两个不相邻的改动即使没有文本冲突，也可能产生行为冲突。

```bash
printf 'mode=combined\n' > settings.txt
git add settings.txt
git diff --cached -- settings.txt
git commit -m 'combine the two learning modes'
git status --short
```

在这个构造例子里，最终文件应只有一行 `mode=combined`，最后状态应为空。真实规则当然不能随意命名一个新值；这里专门用无业务意义的字符串，让注意力集中在合并状态的变化。

## 给合并留下验证证据

实际项目应重新运行受影响的测试，检查配置含义、错误路径以及调用方是否仍然成立。合并提交保存的是一个新的结果，而不是对其中某个分支的机械认可。评审说明中写清冲突涉及的规则和采用结果，便于后续理解为什么没有原样保留任何一边。

练习一次中止路径：重新构造冲突，在没有额外编辑的前提下执行 `git merge --abort`，确认回到合并前状态。不要在带有未提交真实工作的目录里实验中止或恢复；先把练习与工作隔离。关于冲突、中止以及合并前检查，参见 [Git merge 官方说明](https://git-scm.com/docs/git-merge)。
