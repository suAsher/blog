## 先有一个可检查的小变化

以下文件应写在新建的练习仓库里。它只检查传入字符串，不访问网络，不读取配置文件。把业务边界缩小后，测试失败的位置才容易解释。

```python
# validate.py

def valid_name(value):
    return bool(value.strip()) and len(value) <= 40

if __name__ == "__main__":
    assert valid_name("experiment-a")
    assert not valid_name("   ")
    assert not valid_name("x" * 41)
    print("3 checks passed")
```

```bash
python3 validate.py
git add validate.py
git diff --cached --check
git diff --cached --stat
```

预期输出包含三项检查通过；空白检查成功时通常没有输出。统计只告诉你变化规模，无法代替阅读正文。真正的提交前检查仍然需要打开暂存差异，确认没有把凭据、数据集或调试输出带进去。

## 一份提交只回答一个问题

好的粒度来自一个完整意图，而不是固定的行数。新增参数验证时，验证规则、失败案例和必要说明可以一起提交；顺手改一大片格式则会掩盖真正的行为变化。评审者应能从提交标题理解触发条件，再从测试看见前后结果。

写“修复输入检查”仍然略显宽泛，可以明确成“拒绝空白实验名称”。这不意味着标题要重复所有代码细节，而是让未来寻找这段规则的人能够猜到该看哪份记录。对于一次可回退的变化，少量解释往往比长篇描述更可靠。

## 练习与边界

将最大长度从四十改为二十，先添加一个应失败的边界断言，再修改实现。验证通过后，在同一个提交里收录规则和断言。最后用 `git show --stat` 观察本次快照，再用 `git show` 检查实际差异。

这里的脚本是教学校验器，不是生产级名称策略，也没有处理 Unicode 规范化或字节预算。项目规模增大后可迁移到正式测试框架，但“先说明边界，再保存证据”的顺序仍然适用。脚本输出只证明这三个案例，不证明所有输入安全。暂存区差异与提交内容的关系可继续查阅 [Git diff](https://git-scm.com/docs/git-diff)。
