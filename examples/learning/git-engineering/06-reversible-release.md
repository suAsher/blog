## 发布单先记录三个对象

一次博客更新至少涉及源码提交、构建产物和可变内容。它们相关，却不是同一个版本号。下面是教学发布单，不是可直接在服务器执行的脚本；其中所有值都要由本次实际构建和备份产生。

```json
{
  "sourceCommit": "actual-commit-from-git",
  "artifactDigest": "sha256-of-built-package",
  "previousRelease": "previous-directory",
  "backupReceipt": "private-backup-reference",
  "contentSchema": 1
}
```

源码提交说明你审查过什么，产物摘要说明你上传的文件是否一致，备份记录说明出错后能够恢复哪份状态。只写“已经部署最新版”会把这三种问题混在一起，下一次排查就只能依靠猜测。

## 回退不只有换一个目录

静态界面通常可以通过切换版本目录恢复，但后端若已经写入新的字段或改变文件布局，旧程序未必能安全读取并重新保存新数据。回退前要判断兼容性，而不是把“旧二进制能启动”视为足够证据。数据备份与程序版本需要形成一个一致的恢复点。

一个小系统可以选择短暂维护窗口：停止唯一写入进程，创建受保护的内容备份并验证，然后切换程序、检查健康、验证读写，最后恢复正常访问。具体命令要适应自己的部署架构，本节不修改服务器，不默认你具有任意云主机的授权。

## 让练习可以离线完成

在临时目录准备 `release-a` 与 `release-b` 两个文本文件夹，分别放入不同版本说明。写一份发布单，记录哪个目录是当前、哪个是上一个；再模拟新版本失败，按记录恢复读取旧目录。随后增加一个“数据格式变化”条件，写出为什么此时不能只换目录。

演练结果应是一份可检查的操作次序和明确停止条件，不是笼统保证零故障。真实发布时还要验证证书、鉴权和其他共享服务是否保持工作。提交和合并只是交付链的一部分，不能代替内容一致性检查；合并行为的基础可参见 [Git merge 文档](https://git-scm.com/docs/git-merge)。
