## 一条命令必须能诚实失败

把下面内容写到练习项目的 `check.sh`。它只调用同目录的教学测试，不访问托管平台，也没有上传行为。保存后用 `sh check.sh` 执行，不需要修改系统权限或安装后台任务。

```sh
#!/bin/sh
set -eu
cd "$(dirname "$0")"
python3 -m unittest discover -s tests -p 'test_*.py'
git diff --check
```

前提是练习项目确实有 `tests` 目录和测试文件。不要把“命令成功退出”直接等同于“执行了预期数量的测试”：很多工具允许零测试也成功。因此第一次运行应人工核对收集数量，并故意让一个断言失败，确认脚本返回非零且不继续后续检查。

把上一节的小校验器作为 `validate.py` 放在项目根目录，再创建 `tests/test_validate.py`：

```python
import unittest
from validate import valid_name

class NameTests(unittest.TestCase):
    def test_accepted(self):
        self.assertTrue(valid_name("experiment-a"))

    def test_blank_rejected(self):
        self.assertFalse(valid_name("   "))
```

这时应收集两项测试。故意把第二项断言改成 `assertTrue`，用于验证失败路径，然后恢复。

## 自动化首先是一份输入约定

持续集成可以在远端运行同一条命令，但测试框架、工作目录、环境和依赖必须与约定一致。把所有检查藏在某台电脑的编辑器插件里，别人就难以复现；把脚本放进版本库，检查行为才会跟随代码一起评审。

环境变量尤其需要区分必填项与可选项。缺少必要配置时应明确失败，而不是静默跳过整套测试。依赖版本要由项目现有锁文件或工具链约定管理；缓存只是加速工具，不是验证已经发生的证据。缓存命中后仍应执行该执行的断言。

## 练习一条失败链

创建一个最小的标准库 `unittest` 文件，包含一个成功断言和一个故意失败断言。观察终端中的失败数量及退出码，修好断言后再次运行。然后在说明里记录“多少测试、哪个命令、怎样制造失败”，不要只留一句“本地通过”。

这个脚本没有部署步骤，也不包含凭据。后续接入任意CI平台时，优先复用脚本而不是在平台页面重新实现另一套规则。`git diff --check` 只检查相关空白错误，不能发现逻辑漏洞；其能力边界见 [Git diff 说明](https://git-scm.com/docs/git-diff)。任何安全与兼容结论仍然需要针对性的测试。
