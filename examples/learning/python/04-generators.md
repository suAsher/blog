## 不必先把所有结果装进列表

生成器函数遇到 `yield` 时交出一个结果，并保留继续执行所需的状态。调用函数本身还没有遍历全部输入。下面从三行演示文本逐条解析整数：读者可以先取一个，再决定是否需要余下内容。示例不打开文件，也不会读取任何本机业务数据。

```python
def integers(lines):
    for line in lines:
        value = line.strip()
        if value:
            yield int(value)

stream = integers(["1\n", "\n", "3\n"])
print(next(stream))
print(list(stream))
print(list(stream))
```

输出为 `1`、`[3]`、`[]`。最后一次为空，是因为生成器已经耗尽，而不是因为原始数据被改写。若想重新处理，应该建立新的生成器。这个区别对日志处理很重要：一个可迭代输入是否能被反复遍历，需要明确约定，不能靠“它看起来像列表”来猜测。

## 失败也会延迟出现

把第二个有效值改成 `oops`，创建生成器仍可能成功，但遍历到该行时会抛出 `ValueError`。因此异常处理应包住实际消费过程。仅在创建对象时写 `try`，随后把遍历放到别处，会错过你原本打算处理的错误。记录行号能帮助读者找到坏输入，但不要把完整敏感日志拼进公开报错。

## 文件的所有者要看得见

如果生成器内部打开文件，提前停止消费时该文件何时关闭就必须被设计。一个更直观的入门约定是让调用者用 `with path.open(...) as file` 管理句柄，再把 `file` 传给解析生成器，并在这个上下文内完成消费。不要把依赖已关闭文件的生成器带出上下文后再返回。

惰性处理通常减少一次性结果分配，但并非自动实现有界内存：下游若立刻调用 `list`，仍然把所有结果放入内存；内部缓存也可能增长。练习用 `sum(integers(...))` 消费数据，再用 `enumerate` 给错误附上行号，并说明哪些层负责打开、解析与关闭。
