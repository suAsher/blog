## 先定义一个可以单独验证的约定

函数并不只是给几行代码起名字。它是输入、结果和失败方式之间的约定。下面把并发上限的读取收拢为纯函数：不访问文件、环境变量或网络，调用者只需要提供字符串。纯函数容易验证，也让后面的命令行解析与文件读取有清楚的分工。

```python
def parse_limit(text: str) -> int:
    try:
        limit = int(text)
    except ValueError as error:
        raise ValueError("limit must be an integer") from error
    if not 1 <= limit <= 32:
        raise ValueError("limit must be between 1 and 32")
    return limit

for raw in ["4", "0", "bad"]:
    try:
        print("limit", parse_limit(raw))
    except ValueError as error:
        print("invalid", str(error))
```

输出先是 `limit 4`，然后是两个带原因的 `invalid`。类型注解说明希望接收和返回什么，并不会自动在运行时检查所有传入对象。调用者若传入错误的对象类型，可能抛出另一种异常；这也是接口边界需要验证的理由，而不是省掉校验的理由。

## 异常应在能够决定下一步的位置处理

函数内部把整数转换错误补充为领域含义，`from error` 保留原始原因。外层知道自己正在逐条处理演示输入，因此捕获预期的 `ValueError`，打印错误并继续下一项。如果在最底层捕获所有 `Exception` 再返回零，上层将无法区分参数无效与合法结果。日志也不应成为把异常完整复制到公共接口的借口，错误信息需要适合当前读者。

## 让接口不依赖隐含环境

不要在函数里偷偷读取全局配置，也不要让可变列表充当默认参数存储跨次调用的结果。把必要输入明确传入，把新的结果明确返回，这比到处共享一个状态字典更容易推理。等到真正需要缓存或连接池时，再明确它的所有者和生命周期。
